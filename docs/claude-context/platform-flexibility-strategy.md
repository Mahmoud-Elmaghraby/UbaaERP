
# استراتيجية المرونة متعددة الصناعات (Plan + Self-Service) — التصميم + التنفيذ الجاري

**الحالة:** التصميم الاستراتيجي معتمد (بعد نقاش وبحث تنافسي مفصّل — الأقسام اللي تحت "التصميم النهائي المُقترح"). **التنفيذ الفعلي مكتمل لمرحلة orchestrator "مين هيقوم بالدور"** — Layer 1 و Layer 2 مبنيين بالكامل backend وfrontend، والـ orchestrator مبني ومُتحقَّق منه ومكتمل الـ commit لسلسلتي المبيعات والمشتريات الاثنتين. باقي الأقسام محفوظة زي ما هي كسجل تاريخي لقرارات التصميم والبحث التنافسي اللي وصلنا بيه للتصميم الحالي.

## حالة التنفيذ (يُحدَّث مع كل خطوة)

### ✅ منجز — الطبقة الأساسية: Plan / PlanFeature / PlanFeatureGuard (Commit `3d507a6`)

بُنيت أول شريحة حقيقية من طبقة الـ Plan (Layer 1 من التصميم أدناه)، وتم تطبيقها كـ proof of pattern على **موديول المحاسبة بالكامل** (كل الـ 8 controllers) قبل التوسع لباقي الموديولات:

- **Prisma (public schema):** موديلين جداد `Plan` (`key`, `name`, علاقة بـ `PlanFeature[]`) و `PlanFeature` (`planId` + `featureKey`, unique). `Tenant` اتضاف له `planId` (nullable) + علاقة. Migration مكتوبة يدويًا: `20260907054704_add_plans_and_features`.
- **Feature catalog** (`apps/api/src/shared/plans/feature-catalog.ts`): يحتوي مفتاح `accounting` + كل مفاتيح مستندات المبيعات/المشتريات معرّفة مسبقًا (`sales.quotations`, `sales.sales_orders`, `sales.deliveries`, `purchases.rfq`, `purchases.supplier_quotations`, `purchases.purchase_orders`, `purchases.goods_receipts`).
- **`PlanResolverService`:** بيحل مفاتيح الفيتشرز المتاحة للتينانت حسب باقته. **قاعدة أمان مهمة:** لو التينانت مالوش `planId` (null) بيرجع كل المفاتيح (fail-open) — عشان أي تينانت حالي أو تجريبي متقفلش فجأة لحظة نشر الـ guard.
- **JWT:** `features: string[]` اتضافت لـ `JwtAccessPayload`، بتتحسب في `AuthService.issueTokens()` بالظبط زي `permissions` الموجودة.
- **`PlanFeatureGuard` + `@RequireFeature`:** نسخة مطابقة لـ `PermissionsGuard`/`@RequirePermissions` الموجودين. "مفيش metadata = مسموح" افتراضيًا.
- **الـ 8 controllers بتوع المحاسبة:** كل واحد فيهم `@UseGuards(JwtAuthGuard, PermissionsGuard, PlanFeatureGuard)` + `@RequireFeature(FEATURE_KEYS.ACCOUNTING)`.
- **Provisioning:** أي تينانت جديد بياخد باقة "core" (كل المفاتيح) تلقائيًا. سكريبت `pnpm --filter api db:seed-plans` بيزرع الباقة دي (idempotent).

**تحقق:** `pnpm --filter api typecheck` و `pnpm lint` (من الـ root) و `pnpm --filter api test` كلهم عدوا بنجاح فعليًا على جهاز المستخدم.

### ✅ منجز — توسيع الـ Guard على مستندات المبيعات والمشتريات الاختيارية (Commit `d3401a9`)

نفس نمط `PlanFeatureGuard` بالظبط، مطبّق على 7 controllers (المفاتيح كانت موجودة بالفعل في الـ catalog من الشريحة الأولى):

- **المبيعات:** `QuotationsController` → `SALES_QUOTATIONS`، `SalesOrdersController` → `SALES_SALES_ORDERS`، `DeliveriesController` → `SALES_DELIVERIES`.
- **المشتريات:** `RfqsController` → `PURCHASES_RFQ`، `SupplierQuotationsController` → `PURCHASES_SUPPLIER_QUOTATIONS`، `PurchaseOrdersController` → `PURCHASES_PURCHASE_ORDERS`، `GoodsReceiptsController` → `PURCHASES_GOODS_RECEIPTS`.

كل واحد فيهم دلوقتي `@UseGuards(JwtAuthGuard, PermissionsGuard, PlanFeatureGuard)` + `@RequireFeature(FEATURE_KEYS.<KEY>)`. كمان اتحدّثت class-comments بتاعة `sales.module.ts`، `purchases.module.ts`، و `accounting.module.ts` عشان توضح بدقة مين اتغطى ومين لسه.

**قرار نطاق واضح ومقصود (تمت مراجعته مع المستخدم):** الأتي فضل *برة* نطاق هذه الشريحة، وده قرار متسق مع التصميم النهائي (الفاتورة إلزامية دايمًا، باقي المستندات غير المذكورة دلوقتي مؤجلة):
- `CustomersController` / `SuppliersController` — بيانات أساسية، مش خطوة في السيكل.
- `SalesInvoicesController` / `PurchaseInvoicesController` — الفاتورة إلزامية دايمًا، غير قابلة للإيقاف أبدًا.
- `PaymentsReceivedController`، `PurchaseRequisitionsController`، والـ Returns/Credit Notes/POS controllers — كل دول بعد الفاتورة أو مش جزء من سلسلة المستندات القابلة للتخطي اللي التصميم بيتكلم عنها. لو حابب نضيف تحكم لأي منهم لاحقًا، ده قرار منفصل.

**تحقق:** 38 test suite / 358 test كلهم عدوا بنجاح فعليًا على جهاز المستخدم (بعد تشغيل `docker compose up -d` لأن الداتابيز المحلية كانت مقفولة — مشكلة بيئة، مش كود). `pnpm lint` عدى نظيف. Commit نظيف، 10 ملفات، زي المتوقع بالظبط.

### ✅ منجز — Layer 2: التحكم الذاتي للتينانت — Backend (Commit `27c2fd3`)

الطبقة الثانية من التصميم (تحكم صاحب الحساب بنفسه، *جوه* حدود باقته) — Backend بالكامل:

- **Migration جديدة** (`0069_create_tenant_feature_toggles`, tenant schema): جدول `tenant_feature_toggles` — `feature_key` + `enabled` + `updated_at`. مفيش صف = الميزة شغالة (fail-open، نفس فلسفة Layer 1).
- **`TenantFeatureTogglesRepository`** (`shared/plans/`, مسجّل Global جوه `PlansModule` بجانب `PlanResolverService`) — بيقرا/يكتب الجدول، بنفس أسلوب race-condition handling بتاع `KyselyTenantSettingsRepository.getOrCreate()` (INSERT، وعند تعارض unique يتحول UPDATE).
- **`PlanFeatureGuard` بقى بيتحقق من طبقتين:**
  1. الباقة (`features[]`) — زي الأول، بتقفل حتى القراءة (GET) لو الباقة مش شاملة الميزة.
  2. لو الطلب غير GET (إنشاء/تعديل/حذف)، تحقق تاني: هل التينانت قفلها بنفسه (`disabledFeatures[]`)؟ لو قفلها، 403. **القراءة تفضل شغالة دايمًا** (بيانات قديمة تتعرض، بس مفيش إنشاء جديد) — القرار اللي المستخدم اختاره صريحًا، ومطابق لسلوك SAP B1/ERPNext لما يتقفل مستند اختياري.
- **JWT:** حقل جديد `disabledFeatures: string[]` بيتحسب في `AuthService.issueTokens()` بالظبط زي `features`/`permissions` — نفس مبدأ الـ staleness المقبول فعليًا في المشروع (يحتاج تسجيل خروج/دخول عشان يظهر تأثيره).
- **Endpoint جديد `GET/PATCH /feature-toggles`** جوه موديول Settings (`settings.manage` — أي مستخدم عنده الصلاحية دي، مش الـ Owner فقط، حسب قرار المستخدم، ومفروضة على كل الـ methods بما فيها الـ GET). الـ GET بيرجّع كل المفاتيح مع `grantedByPlan` (Layer 1) و `enabled` (Layer 2). الـ PATCH بيرفض تفعيل مفتاح الباقة مش شاملاه (400/422)، بس بيسمح بإيقافه حتى لو الباقة مش شاملاه (مفيش ضرر، أصلاً مقفول من مكان تاني).
- **Contracts:** `libs/contracts/src/settings/feature-toggle.contract.ts` (`featureToggleSchema`, `updateFeatureToggleSchema`).

**تحقق:** `pnpm --filter @erp-platform/contracts build` (خطوة لازمة قبل الـ typecheck، لأن الباكيدج بيتقرا من `dist/` مش من الـ source مباشرة) → `pnpm --filter api typecheck` نظيف → `pnpm lint` نظيف → `pnpm --filter api test`: **39 suite / 365 test عدوا بنجاح**. Commit نظيف، 15 ملف (6 جداد + 9 تعديل)، زي المتوقع بالظبط.

### ✅ منجز — Layer 2: تبويب "الموديولات" — Frontend (Commit `21366d1`)

تبويب جديد جوه صفحة الإعدادات الحالية، بيستهلك `GET/PATCH /feature-toggles`:

- **`apps/web/src/features/settings/modules-tab.tsx`** (جديد): جدول بصف لكل مفتاح فيتشر من الكاتالوج. عمود "حالة الباقة" (Badge للقراءة فقط — `grantedByPlan`، Layer 1) وعمود "مفعّل" (`Checkbox` — `enabled`، Layer 2، مقفول ومعطّل لو الباقة مش شاملة الفيتشر، مع `title` كتلميح). استخدمنا `Checkbox` الموجود بالفعل بدل إضافة `Switch` جديد — مفيش `Switch` في `@erp-platform/ui` أصلاً، و`taxes-tab.tsx` بيستخدم نفس النمط لحقل `isActive` البوليني، فمفيش داعي نضيف dependency/primitive جديد لمجرد التناسق البصري.
- **صلاحية الوصول:** بما إن الـ endpoint نفسه بيفرض `settings.manage` على الـ GET كمان (مش زي باقي التابات اللي القراءة فيها مفتوحة لأي مستخدم مسجّل)، التبويب بالكامل (مش بس أزرار الكتابة) متلفوف بـ `<Can permission="settings.manage" fallback={...}>`، والـ query نفسه (`useFeatureToggles(enabled)`) بيتقفل بمعامل `enabled` عشان المستخدم اللي معاهوش الصلاحية ميعملش طلب 403 لغرض لا داعي له.
- **`queries.ts`:** `useFeatureToggles(enabled = true)` و `useUpdateFeatureToggle()` تحت بانر `// --- Feature toggles (Layer 2 self-service) ---`، بنفس نمط باقي الـ hooks في الملف.
- **`settings-page.tsx`:** `TabsTrigger`/`TabsContent` جداد بـ `value="modules"`.
- **i18n (`ar.json`):** مفتاح `settings.tabs.modules` + قسم `settings.modules` بالكامل (وصف، عناوين الجدول، رسائل نجاح/فشل، تلميح عدم توفر الفيتشر في الباقة). أسماء الموديولات المقروءة نفسها مبنية كـ object متداخل `settings.modules.features.<key>` (مثلاً `sales.quotations` → `features.sales.quotations`) — مستفيدين من إن `react-i18next` بيفصل مسار المفتاح على النقاط بشكل افتراضي، فمفتاح الفيتشر الخام من الباكيند (اللي هو بالفعل نص فيه نقطة) بيتحول تلقائيًا لمسار متداخل صحيح من غير أي map يدوي أو escaping.

**تحقق:** فحص توازن الأقواس وصحة JSON برمجيًا (نظيف). المستخدم شغّل `pnpm --filter web typecheck`/`build`/`lint` على جهازه وأكد إن كل حاجة شغالة تمام. Commit نظيف (`21366d1`)، 4 ملفات (1 جديد + 3 تعديل)، زي المتوقع بالظبط. **Layer 1 و Layer 2 دلوقتي منجزين بالكامل backend + frontend.**

### ✅ منجز ومتحقَّق منه — Invoice-takeover orchestrator، سلسلة المبيعات فقط (Commit `6fcc1ce`)

أول جزء حقيقي من "قاعدة مين هيقوم بالدور" — مبني بس على سلسلة المبيعات (عرض سعر→أمر بيع→تسليم→فاتورة)؛ المشتريات مؤجلة كخطوة تالية منفصلة (قرار صريح من المستخدم عبر `AskUserQuestion`، راجع القسم التالي).

**القرار المعماري المؤكَّد من المستخدم (عبر `AskUserQuestion`):** الفاتورة المباشرة تحترم حالة تفعيل التينانت الفعلية — تتاح **بس** لما الخطوة (أمر البيع أو التسليم) تكون **مقفولة فعليًا** لهذا التينانت (Layer 1 + Layer 2 مجتمعين). لو أمر البيع مفعّل، مفيش طريقة تتجاوزه — النظام يرفض ويطلب إنشاء أمر بيع أولاً. هذا يحافظ على قرار التينانت نفسه (بعكس POS، اللي مش مربوط بحالة التفعيل خالص لأنه مسار مختلف تمامًا).

**التنفيذ:**

- **`FeatureAvailabilityService`** (جديد، `apps/api/src/shared/plans/feature-availability.service.ts`، مسجّل Global جوه `PlansModule`): بيجمع Layer 1 (`PlanResolverService.resolveFeatureKeysForSchema`) و Layer 2 (`TenantFeatureTogglesRepository.listDisabledFeatureKeys`) في boolean واحد `isEnabled(db, schema, featureKey)` — نفس منطق `FeatureTogglesService.list()` بالظبط (`grantedByPlan && enabled`)، بس متاح لكود التطبيق يستخدمه مباشرة في قرارات business logic، مش بس لـ Guard على مستوى HTTP.
- **`SalesInvoicesService.create()` بقى بيقبل مسارين:**
  1. **المسار الحالي** (`salesOrderId` + `lines`) — زي ما هو تمامًا، صفر تغيير في السلوك.
  2. **المسار المباشر الجديد** (`customerId` + `directLines` بدل `salesOrderId`) — بيتقبل **بس** لو `SALES_SALES_ORDERS` مش مفعّلة فعليًا للتينانت؛ لو مفعّلة، بيرفض برسالة واضحة ("Sales Orders is enabled for this tenant — create a sales order first"). لو مقبول، بينشئ ويأكّد أمر بيع (`SalesOrdersService.create/confirm`) داخل نفس الـ transaction، بنفس نمط `PosSalesService.checkout()` تمامًا (إعادة استخدام الخدمة نفسها، صفر تكرار منطق).
  3. **مستقل عن أي من المسارين:** لو `SALES_DELIVERIES` مش مفعّلة فعليًا للتينانت، بينشئ ويأكّد تسليم (`DeliveriesService.create/confirm`) تلقائيًا داخل نفس الـ transaction، يغطي بالظبط كمية هذه الفاتورة (مش الأوردر كله — عشان يدعم فواتير جزئية متعددة على نفس الأوردر بشكل صحيح). لو التسليم مفعّل، السلوك يفضل زي ما هو (مفيش تسليم تلقائي — نفس المخاطرة المقبولة الموجودة فعلاً من قبل).
- **حماية من ازدواج التسليم (bug حقيقي لقيته واتفاديته قبل ما يتكتب):** `PosSalesService.checkout()` بينشئ ويأكّد تسليم كامل للأوردر **دايمًا**، بغض النظر عن حالة تفعيل `SALES_DELIVERIES` (لأن POS مسار مختلف تمامًا مش مربوط بالتفعيل خالص). لو `SalesInvoicesService.create()` كان هينشئ تسليم تلقائي تاني من غير ما يتأكد إن فيه تسليم موجود بالفعل، ده كان هيسبب ازدواج تسليم فعلي (كمية مخزون تتخصم مرتين). الحل: قبل إنشاء أي تسليم تلقائي، بيتحقق من `DeliveryLineRepository.sumDeliveredQuantityBySalesOrderLineIds()` وبيسلّم بس الكمية المتبقية غير المُسلَّمة فعليًا لكل سطر — لو الأوردر مُسلَّم بالكامل من قبل (زي حالة POS)، مفيش تسليم تلقائي جديد أصلاً.
- **`pos-sales.service.ts`:** تعديل صغير واحد فقط — تمرير `schema`/`actorUserId` الجديدين لـ `salesInvoices.create()` (كان الاستدعاء الوحيد الموجود لـ `create()` في الكودبيز كله، تم التأكد بالـ grep).
- **Contracts:** `libs/contracts/src/sales/sales-invoice.contract.ts` — `salesOrderId`/`lines` بقيا optional، وأضيف `customerId`/`directLines` (`createSalesInvoiceDirectLineSchema`) و `warehouseId` اختياري (مطلوب فعليًا بس لما يُحتاج تسليم تلقائي).
- **Quotations:** مفيش أي تغيير مطلوب — `SalesOrdersService.create()` أصلاً بيدعم إنشاء مباشر بـ `customerId`+`lines` من غير عرض سعر، فتعطيل عرض السعر مش محتاج orchestration خالص.

**تحقق (فعلي، على جهاز المستخدم):**
- `pnpm --filter @erp-platform/contracts build` → `pnpm --filter api typecheck` → `pnpm lint` → `pnpm --filter api test`: **365/365 test عدوا بنجاح**، صفر رجعات.
- Suite واحد (`permissions-enforcement.e2e-spec.ts`) طلع فاشل من أول تشغيل، بسبب timeout في hook التنظيف (`afterAll → app.close()`) مصحوب بأخطاء `OutboxDispatcherService` ("driver has already been destroyed") — تم التحقق إنه **flake في التيردون مش رجعة من الكود**: (أ) نفس الملف عدى **7/7** لما اتشغّل لوحده منفصل، و(ب) الملف ده مالوش أي علاقة بموديول Sales وده الملف الوحيد اللي فشل من أصل 39 suite. السبب الجذري المرجّح: `OutboxDispatcherService` عنده interval/cron مش بيتقفل نظيف وقت `app.close()` لما كل الـ e2e suites بتتشغل مع بعض — ده تِك دِبت موجود من قبل، مش ناتج عن هذه الشريحة، ومسجّل هنا للمرجعية لو احتاج فريق آخر يعالجه لاحقًا.
- فحص توازن الأقواس + فحص syntax حقيقي بـ `ts.transpileModule()` (مع `experimentalDecorators`/`emitDecoratorMetadata` مطابقة لإعدادات Nest) على كل الملفات الجديدة/المعدَّلة قبل الـ commit — نظيف بالكامل.
- **Commit `6fcc1ce`** — 8 ملفات (369 إضافة / 90 حذف)، ملف جديد واحد (`feature-availability.service.ts`).

  2. **المسار المباشر الجديد** (`supplierId` + `directLines` بدل `purchaseOrderId`) — متاح **بس** لو `PURCHASES_PURCHASE_ORDERS` مش مفعّلة فعليًا للتينانت؛ لو مفعّلة، بيرفض برسالة واضحة. لو مقبول، بينشئ ويأكّد أمر شراء (`PurchaseOrdersService.create/confirm`) داخل نفس الـ transaction.
  3. **مستقل عن أي من المسارين:** لو `PURCHASES_GOODS_RECEIPTS` مش مفعّلة فعليًا، بينشئ ويأكّد إذن استلام (`GoodsReceiptsService.create/confirm`) تلقائيًا يغطي بالظبط كمية هذه الفاتورة، بنفس حماية "الكمية المتبقية فقط" اللي اتبنيت للتسليم في المبيعات (`GoodsReceiptLineRepository.sumReceivedQuantityByPurchaseOrderLineIds`) — مفيش POS في المشتريات فمفيش سيناريو "منشئ غير مشروط" زي `PosSalesService.checkout()`، لكن الحماية اتبنيت بنفس الشكل على أي حال (رخيصة، وبتحمي من أي استلام سابق موجود على نفس الأمر لأي سبب).
- **اختلاف معماري واحد مقصود عن نسخة المبيعات (موثّق في تعليق الكلاس نفسه):** `DeliveriesService.confirm()` في المبيعات بيكتب لـ Outbox بنفسه (لازم لـ COGS auto-posting)، فـ `SalesInvoicesService.create()` أخد حدث `sales.delivery.confirmed` "مجانًا" لمجرد استدعاء `confirm()`. أما `GoodsReceiptsService.confirm()` **لسه مش Outbox-backed** — لسه بالنمط القديم (الـ controller هو اللي بينشر `purchases.goods_receipt.confirmed` على الـ Event Bus العادي بعد ما الـ transaction بتاعته يتقفل، زي ما هو موضح في تعليق `GoodsReceiptsController.confirm()` نفسه). لو `PurchaseInvoicesService.create()` كان هيستدعي `goodsReceiptsService.confirm()` مباشرة من غير أي تعديل، كان الحدث ده هيتفقد بصمت — يعني إذن استلام يتسجل "مؤكَّد" في الداتابيز من غير ما المخزون يزيد فعليًا أبدًا (Inventory's GoodsReceiptStockListener ملوش أي طريقة تانية يعرف بيها). **الحل المُتخذ (نطاق ضيق، من غير لمس سلوك موجود ومُختبر):** `PurchaseInvoicesService` بقى بياخد `PurchasesEventPublisher` كمان، وبعد ما الـ transaction الخارجية تتقفل بنجاح، لو تم إنشاء/تأكيد إذن استلام تلقائي، بينشر بالظبط نفس الحدث اللي الـ controller كان هينشره (`goods_receipt`, `confirmed`, بنفس الـ metadata shape). **مش اتعدّل `GoodsReceiptsService`/`GoodsReceiptsController` نفسهم خالص** — القرار الأوسع (ترقية `GoodsReceiptsService.confirm()` لـ Outbox زي Deliveries، عشان تناسق معماري كامل) قرار منفصل ومقصود تأجيله، لأنه هيغيّر سلوك موجود لكل استدعاءات التأكيد اليدوية الحالية مش بس مسار الـ orchestrator — محتاج قرار صريح لو حابب نعمله لاحقًا.
- **Contracts:** `libs/contracts/src/purchases/purchase-invoice.contract.ts` — `purchaseOrderId`/`lines` بقيا optional، وأضيف `supplierId`/`directLines` (`createPurchaseInvoiceDirectLineSchema`) و `warehouseId` اختياري.
- **تحسين صغير مصاحب:** رسالة خطأ الـ FK violation في `create()` كانت "The given purchase order or purchase order line does not exist." — تم توسيعها لـ "...supplier, or warehouse does not exist." عشان تغطي الأخطاء الجديدة الممكنة من المسارين الجداد (نفس الرسالة الأدق اللي `SalesInvoicesService` بالفعل عندها).

## القرار المبدئي المتفق عليه (من المستخدم مباشرة)

المستخدم أكد صراحة إنه عايز **الاثنين مع بعض**:
1. **باقات تجارية (Plans)** — مستوى مُدار من جهة المزوّد، بيحدد "السقف" اللي العميل دافع له (أنهي موديولات/فيتشرز متاحة أصلاً لهذا العميل).
2. **تحكم ذاتي (Self-service)** — العميل نفسه، من شاشة الإعدادات، يقدر يفعّل/يقفل حاجات معينة بنفسه من غير تدخل من المزوّد — لكن *جوه* حدود ما تسمح به باقته.

هذا يعني طبقتين منطقيتين لازم تتبنيا معًا:
- **Layer 1 — Plan (عام/تجاري):** `Plan`, `Feature`, `Tenant.planId` في الـ public schema (Prisma). يحدد الحد الأقصى المتاح للتينانت.
- **Layer 2 — Tenant Settings (خاص بكل تينانت):** جدول/أعمدة في الـ tenant schema (Kysely) بيسمح لصاحب الحساب (Owner) يتحكم بنفسه — ضمن حدود Layer 1 — في إيه شغال فعليًا (مثال: قفل موديول المحاسبة، اختيار وضع "الفاتورة المباشرة" بدل السايكل الطويل).
- **الإنفاذ (Guard):** `PlanFeatureGuard` واحد بيتأكد من الشرطين معًا: هل الفيتشر ده أصلاً موجود في باقة التينانت؟ وهل التينانت مفعّله في إعداداته الخاصة؟ الاتنين لازم يكونوا true. ده بيطبّق CLAUDE.md §2.8 حرفيًا (منع الاعتماد على إخفاء الفرونت إند فقط).

**ملاحظة تنفيذية:** الطبقتين (Layer 1 و Layer 2) مبنيتين بالكامل دلوقتي backend وfrontend، وorchestrator "مين هيقوم بالدور" مبني ومُتحقَّق منه ومكتمل الـ commit لسلسلتي المبيعات والمشتريات — انظر "حالة التنفيذ" أعلى المستند.

## آلية "تقصير السلسلة" (Order/PO → Invoice مباشرة) — مبنية على نمط مُثبت بالفعل، مش اختراع جديد

تم التأكيد من الكود الفعلي (`claude/sales-pos-research.md`, `claude/accounting-module-status.md`) إن خصم المخزون وترحيل COGS مربوطين بحدث **تأكيد التسليم (Delivery) / تأكيد الاستلام (Goods Receipt)** — مش بترحيل الفاتورة. يعني أي محاولة نخلي "الفاتورة نفسها تحرك المخزن" لازم تتعامل مع الحقيقة دي، مش تتجاهلها.

الحل المُثبت فعليًا هو نفس نمط الـ POS: `PosSalesService.checkout()` مش بيلغي الأوردر/التسليم — هو بينشئهم برمجيًا في نفس المعاملة الذرية (transaction واحدة، عن طريق `withTransaction` helper) من غير ما يعرضهم كخطوات منفصلة للمستخدم. يعني من ناحية البيانات كل حاجة زي ما هي (Order → Delivery → Invoice كلهم موجودين ومترابطين، وكل الأحداث/الـ listeners شغالة عادي) لكن من ناحية تجربة المستخدم، شاشة واحدة بس.

**التوصية:** نعمم نفس النمط ده (orchestrator واحد بيعمل كل الخطوات في معاملة واحدة) على الشاشات العادية للمبيعات والمشتريات، كخيار ثانٍ ("الوضع المباشر") بجانب السايكل الطويل الموجود — مش بديل يلغيه. هذا **يحافظ على كل منطق الأحداث/المحاسبة/الـ Outbox زي ما هو تمامًا** بدون أي تكرار للمنطق التجاري.

## بحث تنافسي: دوليبار (Dolibarr) — بطلب من المستخدم مباشرة

المستخدم طلب صراحة مراجعة Dolibarr (ERP/CRM مفتوح المصدر معروف بمرونته وانتشاره الواسع مع الشركات الصغيرة والمتوسطة) لفهم إزاي بيدير نفس المشكلة. النتائج (من التوثيق الرسمي ومنتدى Dolibarr):

1. **نظام الموديولات عندهم بسيط جدًا:** كل موديول له مفتاح تفعيل/تعطيل واحد (زرار في `Home > Configuration > Modules`)، بيتحكم فيه الأدمن مباشرة، من غير أي "باقات" مبنية جوه المنتج نفسه — أي تصنيف تجاري (Basic/Pro) بيتم غالبًا بره المنتج (مثلاً مزوّد الاستضافة بيقفل موديولات معينة عن باقة أرخص). هما مش عندهم multi-tenant حقيقي بنفس مفهومنا (schema per tenant) — كل نسخة Dolibarr غالبًا = عميل واحد.
2. **الاكتشاف الأهم:** Dolibarr **بيسمح بعمل فاتورة مباشرة من كارت العميل من غير أمر بيع خالص** — وده مش محتاج "وضع" أو إعداد يتفعّل. الاتنين (الفاتورة المباشرة، أو عرض سعر→أمر بيع→فاتورة) موجودين جنب بعض دايمًا كخيارين، والمستخدم يختار في كل مرة إيه اللي يناسب الحالة. مفيش "مفتاح وضع" بيتغير على مستوى التينانت.
3. **مفيش "معالج إعداد" (wizard) حسب نوع النشاط** — التوثيق نفسه بيقول صراحة إن Dolibarr ما بيقدمش تجميعات جاهزة (bundles) لكل صناعة؛ العميل بيختار موديولاته بنفسه يدويًا. النجاح الواسع للمنتج ده عبر صناعات مختلفة جدًا بيثبت إن البساطة دي كافية عمليًا، ومفيش داعي نعقّد الموضوع بمعالج ذكي من الأول.
4. فيه موديول اسمه "Workflow" بيسمح بأتمتة اختيارية (مثلاً: قفل الأوردر يعمل فاتورة تلقائي) — ده منفصل تمامًا عن فكرة "تخطي خطوة"، وفيه شكاوى موثقة في المنتدى عن روابط بين المستندات بتتكسر لما يتفعّل — يعني نمط مالوش داعي نقلده حرفيًا.

## القرار المُحدَّث بناءً على البحث ده (بديل أبسط من فكرة "وضع السلسلة")

الاكتشاف من Dolibarr غيّر التصميم للأحسن — بدل ما نضيف إعداد/مفتاح "طويل مقابل مباشر" لكل تينانت، الأبسط والأقرب لسلوك مُثبت في السوق هو:

- **تفعيل/تعطيل موديول كامل (زي المحاسبة، أو حتى RFQ/عروض الأسعار في المشتريات)** = ده فعلاً محتاج Guard حقيقي (Plan + إعداد ذاتي) لأنه بيغيّر إيه المتاح في المنيو والـ API خالص.
- **"الفاتورة المباشرة" مقابل "السايكل الطويل"** = **مش إعداد/مفتاح خالص** — الاتنين بيتعرضوا دايمًا جنب بعض كخيارين متاحين لأي تينانت مفعّل عنده موديول المبيعات/المشتريات (بالظبط زي POS، اللي هو أصلاً نفس الفكرة). كل مرة، المستخدم نفسه بيقرر يعمل "فاتورة مباشرة" ولا يعدي بالسايكل الكامل. ده بيلغي أسئلة 2 و3 القديمة تمامًا — مفيش داعي نقرر "مستوى التخطي" مقدمًا، لأن مفيش تخطي بيتقفل، بس بديل دايمًا موجود.

هذا يبسّط التصميم فعليًا لطبقتين واضحتين بس:
- **Guard حقيقي** على الموديولات الاختيارية (محاسبة، RFQ/عروض أسعار، إلخ) — Plan (سقف تجاري) + إعداد ذاتي (تشغيل فعلي جوه السقف).
- **مسارات إنشاء بديلة دايمًا متاحة** (فاتورة مباشرة / سايكل كامل / POS) لأي تينانت عنده الموديول أصلاً — من غير أي إعداد إضافي، فقط شاشات/إجراءات جديدة بتستخدم نفس الـ orchestrator pattern المُثبت في POS.

## الباقات (Plans) — مؤكَّد من المستخدم

**الباقة الأولى** = كل الموديولات الموجودة حاليًا (الإعدادات، المستخدمين والصلاحيات، المخزون، المشتريات، المبيعات بما فيها POS، المحاسبة).
**الباقات اللاحقة** = تضيف موديولات جديدة بالكامل (HR، التصنيع، إدارة المهام/Tasks، وغيرها) — مش تعديلات على الموديولات الحالية، بل موديولات إضافية جديدة تمامًا. هذا يعني `Plan` عمليًا = مجموعة مفاتيح موديولات (module keys)، والباقة الأعلى = تشمل مفاتيح أكتر.

## الحالة الآن

الأسئلة الأربعة الأصلية اتحلت عمليًا:
1. ✅ محلولة — تفعيل الموديول الكامل منفصل تمامًا عن مسارات الإنشاء البديلة (مفيش "وضع سلسلة" أصلاً).
2. ✅ محلولة — الاختيار لحظي دايمًا (مفيش إعداد ثابت للتينانت)، بالظبط زي Dolibarr.
3. ✅ محلولة — مفيش "مستوى تخطي" ثابت يتقرر مقدمًا؛ RFQ/عروض الأسعار تفضل موديول/مسار اختياري منفصل، والفاتورة المباشرة مسار بديل مستقل عن عمق السلسلة.
4. ✅ محلولة — الباقة الأولى = كل الموديولات الحالية، الباقات اللاحقة تضيف موديولات جديدة كاملة (HR/تصنيع/مهام).

## تعديل من المستخدم (بعد الجولة الأولى): تفتيت السيكل بالكامل لموديولات مستقلة

المستخدم طلب توضيح أدق: مش بس "فاتورة مباشرة كخيار جنب السايكل الطويل"— عايز **كل مستند في السيكل يبقى موديول مستقل قابل للتفعيل/الإيقاف بمفرده** (عرض سعر، أمر بيع، تسليم كلٌ على حدة في المبيعات؛ RFQ، عرض سعر مورد، أمر شراء، استلام بضاعة كلٌ على حدة في المشتريات). وسأل: لو العميل قفل "أمر البيع"، مين هيقوم بدوره؟ وطلب صراحة عدم التوقف عند Dolibarr بس، ومراجعة أنظمة تانية للوصول لأفضل شكل.

## بحث تنافسي إضافي: SAP Business One + ERPNext (وODoo كخلفية)

**SAP Business One — أقوى تطابق مع طلب المستخدم، من نظام ERP مؤسسي معروف وموثوق:**
التوثيق الرسمي بيقول حرفيًا: **"فاتورة العميل (A/R Invoice) هي المستند الوحيد الإلزامي في دورة المبيعات... يمكنك إنشاء فاتورة من غير إنشاء أي من المستندات الأخرى."** عرض السعر، أمر البيع، والتسليم كلهم قابلين للتخطي بالكامل. والأهم: **"لو تم تخطي مستند التسليم، حركة المخزون هتحصل عند إضافة فاتورة العميل."** — يعني بالظبط اللي المستخدم واصفه: الفاتورة (المستند اللي لسه شغال) بتاخد دور المستند اللي اتقفل.

**ERPNext — بيقدم بالظبط شكل "المفاتيح المنفصلة" اللي المستخدم طلبه:**
عنده إعدادات صريحة زي `Is Purchase Order Mandatory for Purchase Invoice & Receipt Posting؟` و`Is Purchase Receipt Required for Purchase Invoice Creation؟` — كل واحدة منهم مفتاح مستقل، ومعاها حتى إمكانية استثناء على مستوى مورد معين (`Allow Purchase Invoice Creation Without Purchase Order` في ملف المورد نفسه) — تفصيل أدق مش لازم نبنيه من أول نسخة، بس يوضح إن الفكرة دي معمول بيها فعليًا في نظام إنتاجي منتشر.

**Odoo:** أقل وضوحًا في التوثيق العام، لكنه بيأكد فلسفة "تطبيقات/موديولات منفصلة قابلة للتركيب" بشكل عام (نفس فلسفة Dolibarr)، مفيش تفصيل يضيف حاجة جديدة هنا.

## التصميم النهائي المُقترح (يجمع كل الأنظمة دي + واقع الكود الحالي)

1. **الفاتورة (فاتورة مبيعات / فاتورة مشتريات) هي المستند الإلزامي الوحيد في كل سيكل** — بالظبط زي فلسفة SAP B1 — ومتسقة مع معمارية النظام أصلاً (الفاتورة هي المصدر المالي اللي بيغذي الـ Outbox والمحاسبة).
2. **كل مستند تاني في السيكل (عرض سعر، أمر بيع، تسليم / RFQ، عرض سعر مورد، أمر شراء، استلام) = موديول مستقل تمامًا بمفتاح تفعيل/تعطيل خاص بيه** — زي ما طلب المستخدم بالظبط، ومتوافق مع نموذج ERPNext.
3. **قاعدة "مين هيقوم بالدور" ثابتة ومتوقعة دايمًا:** أقرب مستند لسه شغال (باتجاه الفاتورة) هو اللي بياخد أثر المستند المقفول. لو "أمر البيع" مقفول، الفاتورة (أو التسليم لو شغال) هي اللي هتاخد دوره. لو التسليم كمان مقفول، الفاتورة نفسها هي اللي هتحرك المخزون مباشرة — تمامًا زي قاعدة SAP B1.
4. **آلية التنفيذ الآمنة (خاصة بكودنا احنا):** بما إن حركة المخزون وترحيل التكلفة (COGS) مربوطين حاليًا بحدث تأكيد التسليم/الاستلام (مش الفاتورة)، أأمن طريقة تنفيذ من غير ما نلمس منطق مُختبر وشغال فعليًا هي تعميم نفس نمط الـ POS: أي إنشاء "فاتورة مباشرة" (لما مستند سابق يبقى مقفول) بيعمل المستندات الوسيطة المقفولة **تلقائيًا وبشكل خفي في نفس المعاملة الذرية (transaction)** بدل ما يعرضها للمستخدم كخطوة منفصلة. يعني البيانات والأحداث والمحاسبة تفضل زي ما هي بالظبط (صفر تغيير في منطق مُختبر)، وبس واجهة المستخدم والموديولات المفعّلة هي اللي بتتغير. هذا بيدّي نفس نتيجة SAP B1 (الفاتورة تقوم بالدور) من غير مخاطرة إعادة هيكلة نظام الأحداث.
5. **الفاتورة نفسها غير قابلة للإيقاف أبدًا** — هي الأرضية الإلزامية، مطابق لقاعدة SAP B1 حرفيًا.
