## 2. GoodsReceiptsService → Outbox symmetry — CLOSED 2026-09-12 (natively verified)

**Source:** discovered and deliberately deferred while building the Purchases invoice-takeover orchestrator (commit `41fe5af`); documented in `PurchaseInvoicesService`'s own class comment and in `claude/platform-flexibility-strategy.md`.

**Original state:** in Sales, `DeliveriesService.confirm()` writes its integration event (`sales.delivery.confirmed`) to the Outbox in the same transaction as the status change. In Purchases, `GoodsReceiptsService.confirm()` did **not** — `GoodsReceiptsController.confirm()` published `purchases.goods_receipt.confirmed` on the plain `EventEmitter2`-based Event Bus, after the transaction committed, the older pattern used everywhere before Accounting's Stage 6/7 upgraded Sales' events to Outbox. The Purchases orchestrator worked around this narrowly (injecting `PurchasesEventPublisher` into `PurchaseInvoicesService` to replicate the controller's publish call) rather than fixing the root asymmetry.

**Fixed 2026-09-12** (see the top-of-doc callout's item 3 for the full write-up): `GoodsReceiptsService.confirm()` now takes `schema`/`actorUserId` and writes `purchases.goods_receipt.confirmed` to the Outbox itself, inside the same `withTransaction` call that flips the status and recomputes the parent PO's status — exactly mirroring `DeliveriesService.confirm()`. `GoodsReceiptsController.confirm()` no longer publishes the event itself (it just passes `schema`/`user.sub` through). `PurchaseInvoicesService.create()`'s orchestrator no longer needs its post-commit workaround — that block, the `ownsTransaction`/`autoConfirmedReceipt` bookkeeping, and the now-unused `PurchasesEventPublisher` constructor injection were all removed; it now simply calls `goodsReceiptsService.confirm(trx, receipt.id, schema, actorUserId)` and the event rides along atomically inside its own transaction (via `withTransaction`'s "reuse the open `trx`" behavior). `GoodsReceiptStockListener` (Inventory) needed no changes — it already consumes the event via `@OnEvent('purchases.goods_receipt.confirmed')`, which fires identically whether the event arrives via `OutboxDispatcherService`'s relay or a direct post-commit `publish()` call.

**What a new session should do first:** nothing — this item is closed and natively verified (2026-09-12: `pnpm typecheck`/`test`/`build` confirmed green by the user, see top-of-doc callout). A manual check that confirming a goods receipt actually increases stock is still a reasonable optional follow-up, but is not a tracked gap.

**Why it matters:** was flagged as a real (if latent) risk — any *future* code calling `GoodsReceiptsService.confirm()` directly, bypassing the controller, would previously have silently lost the stock-increase event. That risk is now closed at the source rather than patched per-caller.

Every domain error now carries a `code` (+ optional `params`); `DomainExceptionFilter` returns `{statusCode, code, message}` with `message` in Arabic (looked up in `error-messages.ar.ts`); a new `UnexpectedExceptionFilter` gives the same shape to genuine 500s and other HttpExceptions; `ZodValidationPipe` returns the same shape instead of raw `.flatten()`. There is no more `LEGACY.UNMIGRATED` sentinel left in use anywhere in the six business/platform modules — every throw site across the codebase's application-service layer carries a real code, and every code has a corresponding Arabic entry, each cross-checked by a small Python script (regex over `code: '...'` / `entityNotFound(...)` / `duplicateEntity(...)` call sites, diffed against the catalog's key set) before that module's commit.

**Wording-preservation discipline (only needed for Settings and Users-Permissions, the two modules with real spec coverage):** Purchases, Sales, and Accounting had **no `*.service.spec.ts` files at all** (confirmed by directory listing, not assumed), so those three passes had full freedom on English message wording. Settings and Users-Permissions both have real spec files, so every throw site's spec assertions were checked individually: a spec asserting only the error **class** (`.rejects.toThrow(NotFoundError)`) was free to be reworded or switched to a shared helper; a spec asserting a **message-text regex** (e.g. `/A role named \"Cashier\" already exists\./`) required the original wording to be preserved byte-for-byte, with only `code`/`params` added. In Users-Permissions specifically: `roles.service.ts`'s three bespoke messages (duplicate name, system-role deletion, still-assigned) do **not** match `duplicateEntity`'s generic template and were kept as bespoke `ConflictError` calls with their original text; `users.service.ts`'s duplicate-email message **does** match `duplicateEntity`'s template exactly and was safely converted to use the shared helper.

**A real, expected side-effect surfaced by the Users-Permissions pass:** two e2e specs (`test/e2e/auth.e2e-spec.ts`, `test/e2e/settings-and-users-crud.e2e-spec.ts`) asserted the raw English `response.body.message` text directly via regex (`/invalid email or password/i`, `/cannot deactivate your own account/i`). Since `DomainExceptionFilter` now returns the Arabic-localized message for every caller, not just Users-Permissions, these two assertions broke — correctly, not as a bug. Both were fixed by asserting `response.body.code` (`AUTH.INVALID_CREDENTIALS`, `USER.CANNOT_DEACTIVATE_SELF`) instead, which is exactly what the stable `code` field exists for. Full suite re-confirmed green afterward: 39/39 suites, 365/365 tests, clean `typecheck`, clean `lint`. **Worth a quick grep across the rest of the test suite** (`grep -rn "response.body.message" apps/api/test`) the next time a session touches this area, in case any other e2e spec has the same latent assumption that was simply never exercised by a throw site that got migrated yet.

**What a new session should do:** nothing further is required for this item — it is closed. If a *new* throw site is added to any service going forward, follow the same pattern established here: give it a `code` (+ `params` if the message is parameterized), add the matching Arabic entry to `error-messages.ar.ts`, and prefer `entityNotFound`/`duplicateEntity` over a bespoke message when the generated wording matches what's actually needed.

**Why it matters:** directly requested by the user as part of the refactor initiative (the larger of two scoped options — translating every existing error message, not just building the foundation). This closes out Item (1) of the four-item 2026-09-11 refactor initiative; Item (2) (multi-currency) has now progressed to Phase 1 built (Item 9 below); Item (3) (full module completeness audit) remains open and unstarted.

**A real bug was caught by the new tests, not just written around:** the first native `pnpm --filter api test` run crashed the entire `currency-conversion.service.spec.ts` suite with a cryptic `jest-worker` BigInt-serialization error. Root cause: `CurrencyConversionService.convert()` (built untested in Phase 1) converted amounts via `Number(minorUnits) * Number(rate)` — literal floating-point arithmetic on money, a direct violation of this project's own "no floats for monetary logic" rule. `100 * 1.005` evaluates to `100.49999999999999` in IEEE 754, rounding down to 100 instead of 101, and the resulting failed BigInt comparison is what crashed the test worker rather than failing cleanly.
