# Claude Context Docs

**Purpose:** this folder is a local, in-repo mirror of the working docs Claude (via the "ERP system" Claude Project) keeps about this codebase's build history, decisions, and status — settings/permissions, inventory, purchases, sales, accounting, and the cross-cutting Plan/feature-flexibility, competitive-strategy, attachments, and multi-currency work. It exists so that starting a fresh Claude session (on this account or a different one) with just this repo attached is enough to pick up full context, without needing access to the Claude Project itself (which is tied to one account/organization and doesn't transfer automatically to a different account).

**Source of truth:** the Claude Project ("ERP system") is still the live, actively-updated copy — any future session working from that Project will keep writing there. This folder is a point-in-time export, originally generated 2026-08-31, refreshed 2026-09-10, and **refreshed again 2026-09-13** (all 19 files re-fetched from the live Project and re-written here byte-for-byte; 5 files that didn't exist in this folder before this refresh were added — see the file list below). If you're continuing work from the Project directly, these files may drift slightly behind it over time — ask whichever session is working to re-export this folder after a significant milestone if you want it kept current.

**How to use this with a new Claude session:** attach/open this repo, then point the session at this folder (`docs/claude-context/`) and ask it to read these files before starting — that gives it the same grounding the Project docs give a session with Project access. **Start with `next-steps-backlog.md` first** — it's the newest/most complete handoff file: it names every open item across the whole project, what state each is actually in, and what a new session should check before touching code.

Two contained fixes (General Settings company-profile fields, a Cash Flow Statement report) and one architecture-consistency fix (`GoodsReceiptsService` → Outbox symmetry with Sales' `DeliveriesService`) all shipped and verified 2026-09-12.

Since the 2026-09-10 refresh, two substantial cross-cutting features were researched, built, and fully natively verified, both directly triggered by `module-completeness-audit.md`'s and `competitive-differentiation-strategy.md`'s findings:

- **Shared Attachments infrastructure** (`attachments-strategy.md`) — MinIO-backed file attachments (presigned download URLs) across all 7 planned entity types, backend and frontend both closed and verified 2026-09-12.
- **Multi-currency** (`multi-currency-strategy.md`) — exchange-rate ledger, live-rate sync (frankfurter.dev), and the critical fix making `AccountingAutoPostingListeners` actually convert foreign-currency amounts into the tenant's ledger currency instead of silently discarding the currency field. All 3 phases plus a feature-visibility/self-service-toggle pass are built and fully natively verified as of 2026-09-13.

What's still open — see `next-steps-backlog.md` for full detail on each:
- **Accounting Stage 8 (Tax Returns)** — not started, needs its own research pass.
- **Fixed Assets & Depreciation, Stocktake, ETA e-invoice actual signing/submission, bank-statement import/reconciliation** — all flagged by the competitive-differentiation research as real gaps (some are credibility risks against regional competitors specifically) but none are built yet.
- **Two Settings production-readiness questions** — a real outbound-email provider (still `ConsoleEmailSender`), and confirming the hosting-topology assumption behind `SameSite=Lax` cookies.
- **No automated tests anywhere except Settings/Users-Permissions and the small number of new unit tests added alongside the multi-currency work** — an explicit standing deferral, not an oversight.
- A possible latent bug, flagged but not investigated: a foreign-currency Purchase Order/Invoice might feed an unconverted foreign amount into Inventory's weighted-average cost calculation before Accounting's auto-posting listeners ever see it — not confirmed, not fixed, tracked as an open question.

## Environment note for whoever picks this up next

If continuing via a Claude session with a device-bridge/remote-shell connection to this machine rather than direct native access: that bridge has, at various points in this project's history, been unable to run `pnpm`/`node@24`/`docker` directly (and as of this refresh, `device_bash` itself has been down due to a Windows-update Plan9-drive-share issue — file operations went through `device_stage_files`/`device_commit_files` instead). Treat native verification (`pnpm typecheck`/`lint`/`build`/`test`) as something that needs to be run by the user, natively, in their own terminal, with output pasted back for diagnosis, unless a fresh session confirms the bridge is healthy again. This has been the working pattern for the whole project and is documented in more detail in `settings-module-status.md`'s "Environment notes" section.
