### Stage 7 — Purchase Invoices (done)

The last baseline entity from the master doc's Purchases scope, and this codebase's **first genuinely financial document**. This is also the stage that introduces the Outbox Pattern (CLAUDE.md §2.7 [مستقر]) into the codebase for the first time — new shared infrastructure any future financial event (Sales invoice confirmation, payments, Accounting postings) will reuse.

**The entity itself:**
- **Migration `0038_create_purchase_invoices.ts`:** `purchase_invoices` (invoice_number — OUR issued document number; supplier_invoice_number — the supplier's own bill number, for matching; purchase_order_id → FK; status; invoice_date; due_date; notes; custom_fields) + `purchase_invoice_lines` (purchase_order_line_id → FK, product_variant_id → FK, quantity_invoiced, unit_price as Money VO). `invoice_number` allocated via `NumberingSequencesService` (document_type `purchase_invoice`).
- Same partial-fulfillment shape as Goods Receipts: `create()` validates the PO isn't `draft`/`cancelled`, that every line references a real PO line, and that `quantityInvoiced` doesn't exceed `ordered − already invoiced across every previously *posted* invoice for that line` (`sumInvoicedQuantityByPurchaseOrderLineIds`). `unitPrice` defaults to the PO line's price if omitted. `assertSingleCurrency()` applied from the start.
- No `total_amount` column — computed on read. Status: `draft → posted | cancelled`. `cancel()` only accepts `draft`.

**The Outbox Pattern — new shared infrastructure (`apps/api/src/shared/outbox/`, `apps/api/src/shared/database/`):**
- **Where it lives:** `outbox_events` (migration `0037_create_outbox_events.ts`) is a table in **every tenant schema**, so the outbox write is the same DB transaction as the business write — one more INSERT inside the `trx` the service is already using. Code lives under `shared/outbox/`, genuinely cross-cutting (Sales/Accounting will reuse it).
- **Write side:** `OutboxWriterService.write(trx, eventType, event)`. `PurchaseInvoicesService.post()` is the only place in this module that calls it, instead of the usual controller-level `PurchasesEventPublisher.publish()` — a deliberate divergence, because Outbox correctness requires the write to happen inside the same transaction as the business operation, which only the service method (not the controller, post-commit) can guarantee. `post()` takes `schema`/`actorUserId` as real parameters for exactly this reason.
- **Read/dispatch side:** `OutboxDispatcherService` polls every tenant's `outbox_events` table every 5 seconds (`setInterval`/`OnModuleInit`), claims up to 20 pending rows per tenant per tick via atomic `UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED)`, re-emits each via `emitAsync()` (awaited, unlike the plain Event Bus's fire-and-forget `emit()`) on the same `EventEmitter2` bus. A listener written as `@OnEvent('purchases.purchase_invoice.posted')` doesn't know or care which path delivered it.
- **Reliability upgrade:** a listener that throws causes a retry (up to 10 attempts, then the row is marked `failed` and logged — no dead-letter table yet).
- **New process-level capability, flagged:** the dispatcher enumerates tenants via `public.tenants` — the first time the running API process touches that table outside request-time JWT-based schema resolution. A new `PrismaService`/`PrismaModule` (`shared/database/`) wraps `@prisma/client` (not a new dependency — already used by the standalone migration CLI, just never inside the long-lived app process before), scoped narrowly to only the background dispatcher.
- **Naming:** the real event name is `purchases.purchase_invoice.posted`, matching the established `purchases.<entityType>.<action>` convention.
- **Files:** `shared/database/{prisma.service,prisma.module}.ts`; `shared/outbox/domain/outbox-event.entity.ts`; `shared/outbox/application/ports/outbox-event.repository.ts`; `shared/outbox/application/services/{outbox-writer,outbox-dispatcher}.service.ts`; `shared/outbox/infrastructure/persistence/kysely-outbox-event.repository.ts`; `shared/outbox/outbox.module.ts` (both `@Global()`, registered once in `app.module.ts`). Purchases side: `domain/purchase-invoice.entity.ts`; `application/ports/{purchase-invoice,purchase-invoice-line}.repository.ts`; `application/services/purchase-invoices.service.ts`; `infrastructure/persistence/kysely-{purchase-invoice,purchase-invoice-line}.repository.ts`; `presentation/purchase-invoices.controller.ts`; contract in `libs/contracts/src/purchases/purchase-invoice.contract.ts`. Reuses `purchases.manage` permission. `purchases.module.ts`: 8 services, 14 repository bindings, 1 event publisher.

**Known limitation:** until Accounting (or any listener) registers `@OnEvent('purchases.purchase_invoice.posted')`, the dispatcher still marks every posted invoice's outbox row `processed` on its next tick — `emitAsync()` with zero listeners just resolves immediately. Correct at-least-once semantics, not a bug, but posting an invoice today looks like "nothing happened" beyond the status flip until a real listener exists. **Note from a later session:** this is now resolved — Accounting Stage 3 registers `@OnEvent('purchases.purchase_invoice.posted')`, see `claude/accounting-module-status.md`.

### Frontend Stage 4 — Purchase Orders (done)

**The first entity with two mutually-exclusive creation paths**, mirroring the backend's `resolveSupplierAndLines()` design (`sourceQuotationId` alone, vs. `supplierId` + `lines` given directly — never both). Also the first stage where the Money-line pattern is a real backend-enforced constraint rather than a UI simplification: `PurchaseOrdersService.create()`/`update()` call `assertSingleCurrency()` and reject mixed-currency lines, unlike Supplier Quotations.

- **Two-path create UX as one dialog, two tabs.** `CreatePurchaseOrderTabs` (shadcn `<Tabs>`) wraps `CreatePurchaseOrderFromQuotationForm` and `CreatePurchaseOrderManualForm`. The "from quotation" tab only collects header fields (`expectedDeliveryDate`/`notes`/`customFields`) plus a read-only lines preview fetched via `useSupplierQuotation(selectedQuotationId)` — supplier and lines are copied verbatim from the quotation server-side, so the form never lets the user touch them. The "manual" tab is a full supplierId + line-editor form, structurally identical to `CreateSupplierQuotationForm` from Stage 3 minus the RFQ scoping.
- **New "composed bulk-lookup" hook**, `hooks/purchase-orders/use-eligible-quotations.ts`: finds every supplier quotation that is `status === 'selected'` and doesn't already have a purchase order created from it — a client-side dedup the backend does not itself enforce (nothing stops a second PO from referencing the same quotation). Since a quotation only ever reaches `'selected'` as a side effect of its RFQ closing, this fans out via `useQueries` over every `status === 'closed'` RFQ's quotations (`GET /supplier-quotations?rfqId=`, same query-key shape as `useSupplierQuotations` so the cache is shared — the same "composed bulk-lookup" pattern Inventory's `useProductsWithVariants` already established), then cross-references `usePurchaseOrders()`'s `sourceQuotationId` values to exclude already-used quotations.
- **Money handled the same way as Stage 3's Supplier Quotations**, but now as a real constraint rather than a simplification: every line in the manual-create/edit path takes the selected supplier's own `defaultCurrency` uniformly, which satisfies `assertSingleCurrency()` by construction. `PurchaseOrderLineItemsEditor` is a near-duplicate of `QuotationLineItemsEditor` (deliberately, per the ESLint boundary rule — no cross-entity component import).
- **`totalAmount` is always server-computed, never summed client-side.** `PurchaseOrdersService.getById()` derives it from the lines on every read and never stores it, so `PurchaseOrderDetailsView` renders `order.totalAmount` as-is via `formatMoney()` rather than recalculating from the lines it also displays.

### Frontend Stage 5 — Goods Receipts (done)

**The first cross-module frontend integration point mirroring the backend's own first one** — `confirm()` here is what actually drives a Purchase Order's status into `partially_received`/`fully_received` (the two PO status values Stage 4 could only display). Also the first entity with no edit form at all, and the first with a "receiving worksheet" line editor shaped entirely differently from every prior stage's freeform add/remove-row pattern.

- **No `EditGoodsReceiptForm` — the backend has no `update()` for this entity.** `GoodsReceiptsService`'s own doc comment explains why: a wrong draft is cancelled/deleted and recreated rather than edited in place, keeping the entity's scope tight. The frontend follows suit — `CreateGoodsReceiptForm` is the only form, and the tab's dropdown never offers an edit action.
- **A genuinely new line-editor shape: a receiving worksheet, not a freeform line list.** Every prior stage's line editor (`PurchaseRequisitionLineItemsEditor`, `RfqLineItemsEditor`, `QuotationLineItemsEditor`, `PurchaseOrderLineItemsEditor`) lets the user add/remove arbitrary rows and pick any product per row. A goods receipt can't work that way — you can only receive against lines that already exist on the selected purchase order. `GoodsReceiptLineItemsEditor` instead renders one fixed row per outstanding PO line (product, ordered qty, remaining qty, a quantity-to-receive input, an optional unit cost override, notes); rows left at 0 are simply excluded when the form builds the DTO, so a partial receipt (some lines, or a partial quantity on one line) is the normal case, not a special one.
- **New hook to derive "what's still outstanding" client-side**, `hooks/goods-receipts/use-purchase-order-remaining.ts`: neither `remaining quantity per PO line` nor `already received` is exposed by any single endpoint, so this hook fetches the selected PO's own lines (`ordered`) plus every *confirmed* goods receipt already recorded against that PO (fanned out via `useQueries` over `GET /goods-receipts?purchaseOrderId=`, then `GET /goods-receipts/:id` per receipt for its lines — the list endpoint doesn't include lines, matching the "list-doesn't-include-lines" convention every other entity already follows) — the same "composed bulk-lookup" pattern as Stage 4's `use-eligible-quotations.ts`. This is a client-side convenience only, to build the worksheet and hint at valid input ranges; `GoodsReceiptsService.create()` re-validates the same remaining-quantity cap independently server-side regardless.
- **Second cross-module frontend dependency**, alongside the now-familiar `useProductsWithVariants`: `useWarehouses` from Inventory's `api/warehouses/queries`, to populate the receipt's `warehouseId` select — same read-only reference-data justification as every prior cross-module hook (CLAUDE.md §2.6 doesn't apply).
- **Unscoped list, unlike Supplier Quotations.** `GET /goods-receipts` has no required filter (an optional `?purchaseOrderId=` narrows it, used only internally by the remaining-quantity hook), so Goods Receipts gets its own routed page and plain master list — no master–detail nesting needed here.
- **Status workflow (`draft/confirmed/cancelled`) surfaced status-gated:** confirm/cancel only on `draft`; delete on `draft`/`cancelled`. The confirm action's confirm-dialog explicitly warns that it updates stock and the purchase order's status, matching what `GoodsReceiptsService.confirm()` actually does (recomputes the parent PO's status in the same transaction, then the controller publishes the Event Bus integration event Inventory's listener consumes).
- **`.eslintrc.cjs` widened a fifth time** — added `purchases-goods-receipts`, and all five Purchases entity rules now mutually disallow importing each other's `components/**`. Reloaded via Node to confirm it's still valid (16 elements, 14 rules).

### Frontend Stage 7 — Purchase Invoices (done, this pass — final entity, Purchases frontend now complete)

**The last entity in the Purchases module's frontend scope.** Structurally the closest sibling to Stage 4 (Purchase Orders) rather than Stages 5–6: it's tied to a purchase order (not a goods receipt), carries real Money with a unit-price override (like Purchase Orders/Goods Receipts, unlike Purchase Returns), and uses the same "confirmed/partially_received/fully_received all eligible" PO-status filter logic pattern, re-derived independently from `create()` rather than assumed to match Goods Receipts' narrower filter. It also introduces one new distinction: the "post" terminology and the backend's Outbox write, both carried through faithfully without changing the frontend's shape.

- **No `EditPurchaseInvoiceForm` — confirmed independently, not assumed from precedent.** The contract has no `updatePurchaseInvoiceSchema` and the service has no `update()` method (grepped directly). `CreatePurchaseInvoiceForm` is the only form; the tab's dropdown never offers an edit action — same shape as Goods Receipts and Purchase Returns, but verified fresh for this entity rather than carried over as an assumption.
- **An invoiceable worksheet, mirroring the receiving worksheet from Stage 5 almost exactly**, since both are "outstanding quantity against a purchase order line": `PurchaseInvoiceLineItemsEditor` renders one fixed row per PO line with `remaining > 0` (product, ordered, remaining, quantity-to-invoice input capped at `remaining`, an optional unit-price override defaulting to the PO line's price, notes). Rows left at 0 are excluded from the submitted DTO — a partial invoice is the normal case.
- **New hook**, `hooks/purchase-invoices/use-purchase-order-invoiceable.ts`: fetches the selected PO's own lines (`ordered`) plus every *posted* invoice already recorded against that PO (fanned out via `useQueries` over `GET /purchase-invoices?purchaseOrderId=` then per-invoice line fetches — list endpoints never include lines, the same convention every prior entity follows), sums `quantityInvoiced` per PO line, and computes `remaining = ordered − invoiced`. Matches the backend's own `sumInvoicedQuantityByPurchaseOrderLineIds` filter (`WHERE purchase_invoices.status = 'posted'`), confirmed by reading the actual repository method's SQL rather than assumed. Client-side convenience only; the backend re-validates independently.
- **Eligible-PO filter is `status !== 'draft' && status !== 'cancelled'`** — deliberately wider than Goods Receipts' `'confirmed' || 'partially_received'` filter, because a `fully_received` PO can still be invoiced (invoicing tracks a completely independent "already invoiced" ledger from "already received"). Derived by reading `PurchaseInvoicesService.create()`'s actual validation, not copied from the Goods Receipts precedent.
- **"Post," not "confirm."** Every prior one-way status transition in this module used "confirm" (Goods Receipts, Purchase Returns) or a dedicated verb (RFQ's "send," Supplier Quotation's "select"/"reject"), but the Purchase Invoices controller exposes `POST /:id/post` — the accounting term for finalizing a ledger-worthy document. The frontend follows this exactly: `usePostPurchaseInvoice()`, label "ترحيل الفاتورة" (not "تأكيد"), confirm-dialog copy referencing posting rather than confirming.
- **The Outbox-vs-EventBus split is backend-only and doesn't change the frontend's shape.** The controller's own doc comment explains that `post()` is the one action in the module that does not call `this.events.publish()` — it writes to the Outbox atomically with the status flip instead (CLAUDE.md §2.7). From the frontend's perspective this is still just one more `POST /:id/post` mutation, so `usePostPurchaseInvoice()` is built identically in shape to every other status-transition hook; the distinction is documented in a code comment only.
- **Cancel is stricter than it looks.** `PurchaseInvoicesService.cancel()` only accepts `draft` — the service's own comment explains why: a posted invoice is a ledger-worthy fact, and reversing one needs a real accounting reversal, not a plain cancel. In practice this renders identically to Goods Receipts/Purchase Returns (`status === 'draft'` gating), since all three only ever allow `draft → cancelled` anyway, but the stricter rationale is documented in code for when Accounting reversal exists.
