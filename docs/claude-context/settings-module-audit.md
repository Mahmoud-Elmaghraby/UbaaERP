## 1. Architecture & code quality — verdict: solid, no structural rework needed

- Clean Architecture layering (`domain → application → infrastructure → presentation`) is followed correctly in both modules. No business logic found leaking into controllers or repositories.
- DDD applied selectively and correctly per CLAUDE.md §2.1: Settings is plain CRUD (no unnecessary aggregates), Users & Permissions has just enough invariant-checking (e.g. permission-key filtering, refresh-token rotation) without over-engineering.
- File sizes are healthy — largest backend file is 141 lines (`users.controller.ts`). No god-classes, no god-services. This module does **not** need the kind of restructuring Inventory's frontend redesign proposal is targeting.
- Cross-module coupling is correct: `InventoryAuditListener` lives in `users-permissions/infrastructure/listeners/` and reacts to `inventory.**` over the Event Bus — no direct import, matching CLAUDE.md §2.6.
- Every controller in both modules is `@UseGuards(JwtAuthGuard, PermissionsGuard)` + `@RequirePermissions(...)`, correctly and consistently. `PermissionsGuard` fails closed (throws `ForbiddenException` when a required permission is missing) and reads permissions from the verified JWT, not from client input.
- Tenant isolation is sound: `schema` is embedded in the signed JWT payload (`JwtAccessPayload`) and read via `@CurrentTenantSchema()` everywhere except the necessarily pre-auth `/auth/*` routes — a client cannot pick which tenant schema it operates against by manipulating a header or body field post-login.
- Refresh-token handling is done right: tokens are stored hashed (SHA-256) not in plaintext, rotated on every use (single-use, old one revoked before a new one is issued), and `refresh()`/`login()` both re-check `user.isActive`.
- Frontend follows the established conventions consistently (separate create/edit forms, `<Can>` for permission-gated UI, dynamic custom-fields engine, i18n keys throughout).

**One frontend code-organization note, not urgent:** `numbering-tab.tsx` (379 lines), `templates-tab.tsx` (311), `taxes-tab.tsx` (300) are flat single-file tabs mixing table + form(s) + local state — the same shape the pending Inventory frontend redesign proposal (`claude/inventory-frontend-status.md`) is meant to replace with per-entity subfolders and real routes. Not a bug, but worth doing in the same pass as that redesign rather than separately, so Settings doesn't end up on a different convention than the rest of the app.

## 2. Security gaps — the real findings

These are things that pass every existing test and lint rule but would not pass a security review for a system that will hold financial data. Ordered by how much it would actually hurt if exploited or if it just broke in production, not by how easy each is to fix.

### 2.1 No brute-force protection on login — **High** — ✅ Implemented (this pass)
`POST /auth/login` has no rate limiting (`@nestjs/throttler` is not installed anywhere in `apps/api`) and no account lockout after repeated failures. Nothing stops a scripted password-spray against every email in a tenant. There's also no audit trail for *failed* logins — `AuthService.login()` only calls `auditLogs.record()` on success, so a live brute-force attempt would leave no trace in `audit_logs` at all. Recommendation: add `ThrottlerModule` (IP + email-based) on `/auth/*`, and record failed attempts (`auth.login_failed`) in the audit log the same way successes are recorded.

### 2.2 Access/refresh tokens stored in `localStorage` — **High** — ✅ Implemented (Task 9, this pass)
`apps/web/src/lib/auth-store.ts` persisted `accessToken` **and** `refreshToken` via Zustand's `persist` middleware, which defaults to `localStorage`. Any XSS anywhere in the app (a dependency, a rendered custom field, a future rich-text template field) could read both tokens directly — the refresh token especially is long-lived (30 days) and would let an attacker stay authenticated well past the access token's own TTL. Fixed by moving the refresh token out of the frontend entirely: `POST /auth/login`, `/auth/login/verify-2fa`, and `/auth/refresh` now set it as an httpOnly, `SameSite=Lax` cookie scoped to `/auth` (`Secure` forced on in production); `auth-store.ts` no longer holds a `refreshToken` field at all, and `api-client.ts` sends `credentials: 'include'` on every request instead of a body token. See §7 below for the full implementation and the one deployment-topology assumption this makes explicit.

### 2.3 No password reset ("forgot password") flow — **Medium-High** — ✅ Implemented (this pass)
`UsersController` only has `POST /users/me/change-password`, which requires knowing the *current* password. There is no recovery path for a user who is locked out. Daftra, a named regional competitor, documents this explicitly as a standard feature ("Resetting the Password for the Admin (Owner) and the User"). Today the only recovery path in this codebase is another Owner manually setting a new password via `PATCH /users/:id` — workable for an internal tool, not for a real multi-tenant SaaS.

### 2.4 New users get a password set directly by an admin, not an email invite — **Medium** — ✅ Implemented (this pass, additive)
`POST /users` (`createUserSchema`) takes a password up front — meaning an Owner either has to tell the new user their password out-of-band, or the new user never independently proves control of their own email. Daftra's equivalent is "Sending the Login Details to a User." Same theme as 2.3: no email-based account-recovery/invite infrastructure exists yet anywhere in the codebase (no mail-sending capability was found in `apps/api` at all — worth confirming there's no SMTP/mail service already planned in the master doc before proposing one).

### 2.5 No 2FA/MFA — **Medium** — ✅ Implemented (Task 8, this pass)
Confirmed via research: Odoo has shipped TOTP-based two-factor authentication as a core feature for years (documented through Odoo 19). For a system whose Owner role holds unrestricted access to every financial module, an optional TOTP second factor is a reasonable, well-precedented ask, not gold-plating. Implemented as a per-user opt-in (mirroring Odoo's approach, not a mandatory org-wide setting): TOTP secret + backup codes, a two-step setup flow, and a two-step login flow when enabled. See §7 for the full design.

### 2.6 Permission/deactivation changes aren't enforced until the current access token expires — **Medium, mostly a documentation gap** — ✅ Force-logout implemented (this pass); staleness itself is an accepted, documented trade-off, not "fixed"
Permissions are baked into the JWT at issuance (`issueTokens()`), and `PermissionsGuard` only reads the token, never the database. If an Owner revokes a permission or deactivates a user, that only takes effect once the user's current access token expires and they're forced to `refresh` (`refresh()` does correctly re-check `isActive`) — so the actual exposure window is bounded by the access-token TTL, not unbounded. Worth (a) confirming what `JWT_ACCESS_TTL` actually is in practice, and (b) documenting this as a known, bounded trade-off rather than leaving it implicit — and considering a "force logout" action (revoke all of a user's refresh tokens) for the deactivation case specifically, since that one is a real incident-response need (compromised account, terminated employee).

### 2.7 No security headers (`helmet`), no CORS allowlist by default — **Medium** — ✅ Implemented (this pass)
Confirmed: no `helmet` anywhere in `apps/api`. `main.ts` already has a clear, honest comment flagging that `CORS_ORIGIN` reflects the request's own origin unless explicitly set, "should become an explicit allowlist before any production deployment" — good that this was already self-flagged; it just needs to actually happen, alongside adding `helmet()` for the standard header set (HSTS, X-Content-Type-Options, etc.).

### 2.8 No environment-variable validation at boot — **Low-Medium** — ✅ Implemented (this pass)
`process.env.X ?? default` is scattered ad hoc (`JWT_REFRESH_TTL_DAYS`, `PORT`, `CORS_ORIGIN`, etc.) with no startup-time schema check. A typo'd env var name fails silently into a default rather than failing loudly at boot. Recommend a small Zod-validated config object read once at startup (consistent with the project's existing Zod-first approach, no new library needed).

### 2.9 No password complexity policy — **Low** — ✅ Implemented (this pass)
`changePasswordSchema`/`createUserSchema` were not inspected in `libs/contracts` for length/complexity rules this pass — worth a quick check as part of whichever fix addresses 2.1/2.3, not a separate investigation.

## 7. Implementation status (this pass — built under the user's blanket approval)

**Built and verified (source-level: brace/paren/bracket balance + relative-import resolution, across all 48 touched/created files — clean; content transferred to the repo was additionally byte-verified via sha256 before extraction):**

1. **Failed-login audit logging + rate limiting (2.1).** `AuthService.login()` now records `auth.login_failed` (with `metadata.reason`: `not_found` / `inactive` / `wrong_password`) on every failure path, mirroring the existing success-path audit call. `@nestjs/throttler` registered globally (`ThrottlerModule.forRoot`, 60/min default) plus a tighter `@Throttle({ limit: 5, ttl: 60_000 })` on `/auth/login`, `/auth/login/verify-2fa`, `/auth/forgot-password`, `/auth/reset-password`.
2. **`helmet` + explicit CORS allowlist (2.7).** `app.use(helmet())` added in `main.ts`. `CORS_ORIGIN` is now required (boot throws) when `NODE_ENV=production`; a dev-only console warning is emitted when it's unset outside production, reflecting the request origin as before.
3. **Env validation at boot (2.8).** New `apps/api/src/shared/config/env.validation.ts` — a Zod schema validating `DATABASE_URL`, `JWT_ACCESS_SECRET` (required), plus shape-checks on `JWT_ACCESS_TTL`, `JWT_REFRESH_TTL_DAYS`, `PORT`, `NODE_ENV`, `CORS_ORIGIN`. Called from `bootstrap()` **before** `AppModule` is even imported (the module import was converted to a dynamic `await import('./app.module')` specifically so validation runs first — see note below on why a static import would have defeated the purpose).
4. **Password complexity (2.9).** New shared `strongPassword` Zod schema (min 8, max 128, requires lowercase + uppercase + digit) in `libs/contracts`, applied to both `createUserSchema.password` and `changePasswordSchema.newPassword`. Checked against every existing e2e/integration password fixture first — all already comply, no test breakage.
5. **Password reset flow (2.3).** New `POST /auth/forgot-password` (always returns 204 regardless of whether the email exists — anti-enumeration) and `POST /auth/reset-password`. Backed by a new `account_action_tokens` table (migration `0065`, hashed single-use tokens, `purpose` discriminator, FK cascade on user delete) shared with the invite flow below, and later widened (migration `0068`, see item 9) to also back the 2FA login challenge.
6. **Email-based invite (2.4, additive — not a breaking change to `createUserSchema`).** New `POST /users/:id/invite` sends an invite token via the same `account_action_tokens` mechanism; the admin-set-password flow on `POST /users` is unchanged and still works. A new `EmailSenderPort` abstraction with a `ConsoleEmailSender` placeholder implementation was added — this deliberately does **not** pick a real SMTP/email provider (same "build the readiness, not the external integration" pattern already used for ETA e-invoice credentials elsewhere in this codebase). **The user needs to decide on a real email provider before this is usable in production**; until then, invite/reset emails are logged to the console only.
7. **Force-logout / session revocation (2.6, partial).** `UsersService.revokeSessions()` (new) revokes all of a user's refresh tokens and audits `user.sessions_revoked`; wired to `POST /users/:id/revoke-sessions` (admin-triggered) and `POST /users/me/revoke-sessions` (self-service). Deactivating a user (`isActive: false` via `PATCH /users/:id`) now automatically revokes their sessions too. Frontend: a "Session Security" card was added to the profile page, and a per-row "revoke sessions" action to the users list, both using `window.confirm` (the codebase's established confirmation pattern — no `AlertDialog` usage exists anywhere in this app).
8. **Health check.** New unauthenticated `GET /health`, checks DB connectivity via `PrismaService.$queryRaw`.
9. **Optional TOTP two-factor authentication (2.5, Task 8).** Modeled on Odoo's per-user opt-in approach, not a mandatory org-wide setting:
   - **Data model:** migration `0066` adds `users.totp_secret_encrypted` (AES-256-GCM via the existing `SecretsEncryptionService` — the same shared-kernel service already used for Sales' `eta_credentials.client_secret`, never plaintext) and `users.totp_enabled` (a separate boolean, not "secret IS NOT NULL", because setup is two steps — see below). Migration `0067` creates `user_backup_codes` (one row per single-use recovery code, hashed with SHA-256, same shape as `refresh_tokens`/`account_action_tokens`). Migration `0068` widens `account_action_tokens.purpose` to also accept `'mfa_challenge'`, reusing that table's existing hashed/single-use/expiring guarantees for the login-time 2FA challenge rather than inventing a third token mechanism.
   - **TOTP algorithm:** implemented from scratch on Node's built-in `crypto` (RFC 4226 HOTP / RFC 6238 TOTP, HMAC-SHA1, 30s step, 6 digits, ±1 step drift tolerance) rather than adding a new npm dependency — justified per CLAUDE.md §12 (new dependencies need justification; TOTP is a small, stable, publicly-testable algorithm). `totp.service.spec.ts` verifies against the real published RFC 6238 Appendix B test vectors, independently cross-checked.
   - **Two-step setup:** `POST /users/me/2fa/setup` generates and stores a *pending* secret (does not enable 2FA yet) and returns the secret + an `otpauth://` URI; `POST /users/me/2fa/confirm` requires a valid code against that pending secret before flipping `totp_enabled` to true and issuing 8 backup codes (shown to the user exactly once, only their hashes stored). This avoids leaving an account in a broken 2FA state if setup is abandoned mid-flow (tab closed, app crashed). `POST /users/me/2fa/disable` requires the current password. `GET /users/me/2fa/status` exposes only `{ enabled: boolean }` — never the secret, pending or otherwise, and deliberately not added to the general user profile/list schema.
   - **Two-step login:** `POST /auth/login` now returns either real tokens or `{ mfaRequired: true, challengeToken }` when the account has 2FA enabled (no session issued yet). `POST /auth/login/verify-2fa` redeems the challenge (single-use regardless of outcome) plus a code — a live TOTP code first, then falling back to a single-use backup code — and only then issues tokens. Failed 2FA attempts are audited (`auth.login_failed`, `reason: invalid_2fa_code`); successful 2FA logins are audited with `metadata.via: '2fa'`.
   - **Frontend:** a new `TwoFactorCard` on the profile page (setup → confirm-with-code → one-time backup-codes display, or disable-with-password); the login page gained a second stage (code entry) that appears in place, without navigating away, when the backend signals `mfaRequired`. Deliberately does **not** render a QR code image — adding a QR-generation library is a real dependency decision out of this task's scope (CLAUDE.md §12); the secret and otpauth URI are shown as selectable text instead, which every mainstream authenticator app also accepts via "enter code manually."
10. **httpOnly-cookie refresh-token storage (2.2, Task 9).** The refresh token no longer appears anywhere in a JSON request or response body, or in `localStorage`:
    - `POST /auth/login`, `/auth/login/verify-2fa`, and `/auth/refresh` now set it as an httpOnly cookie (`refresh_token`), `Secure` forced on when `NODE_ENV=production`, `SameSite=Lax`, scoped to `path: '/auth'` (never sent on any other route). `POST /auth/logout` reads and clears the same cookie.
    - `cookie-parser` was added as a new backend dependency (justified: standard Express middleware needed to populate `req.cookies`; no built-in NestJS/Express alternative) and wired in `main.ts` right after `helmet()`.
    - `apps/web/src/lib/auth-store.ts` no longer has a `refreshToken` field at all (removed from both state and the persisted `partialize`); `apps/web/src/lib/api-client.ts` sends `credentials: 'include'` on every request so the browser attaches the cookie automatically, and no longer sends a body token to `/auth/refresh`. `useLogout()` now takes no argument and always calls the real `/auth/logout` endpoint before clearing local state (previously it only called the backend when a refresh token happened to be present client-side).
    - `AuthService` itself is unchanged in what it returns (`AuthTokens` still includes the raw `refreshToken` value) — cookie-vs-body transport is deliberately kept as `AuthController`'s concern, not the service's, per Clean Architecture layering (HTTP transport details don't belong in the application layer).
    - **One explicit, documented assumption, not silently decided:** `SameSite=Lax` assumes the eventual production frontend and API share a registrable domain (confirmed safe against this app's actual tenancy design, which is JWT/header-based, not subdomain-based — tenant resolution never depends on the request's hostname). CLAUDE.md §12 leaves production hosting topology an open decision; if that decision ever puts the frontend and API on genuinely different registrable domains, this needs `SameSite=None` (+ `Secure`, and reconsidering third-party-cookie restrictions some browsers now apply) instead. Flagged in code comments on `AuthController`, not treated as settled.
