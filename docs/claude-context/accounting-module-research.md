# Accounting Module — Research & Build Plan

**Date:** 2026-08-30. CLAUDE.md §10 — step 5, the last module in the fixed build order. Inventory, Purchases, and Sales are all backend-and-frontend complete; this is the competitor-research pass required by §17.2 before/while building Accounting, plus the proposed stage roadmap.

## What prompted this

The user asked directly whether the gaps already flagged in Sales/Purchases (no financial credit note on Sales Returns, stock-movement events on plain EventEmitter2 rather than Outbox, no PlanFeatureGuard) would matter for Accounting — then asked to pave the full way for a complete Accounting module: chart of accounts, fiscal years, journal entries, the works. Before writing any code, the actual repo was inspected (not assumed) to answer that question precisely — see the findings below and `claude/accounting-module-status.md` for what they mean concretely.

## Repo inspection findings (grounding facts, not research, but decisive for design)

- **No `accounting` module exists anywhere in the codebase yet** — confirmed by searching `apps/api/src/modules` before writing anything.
- **The Outbox infrastructure is already correctly wired for every financial document that exists so far**: `PurchaseInvoicesService.post()`, `SalesInvoicesService.post()`, and `PaymentsReceivedService.post()`/`allocate()` all write an outbox row in the same transaction as the status flip (confirmed by reading each service directly, not assumed by analogy). **No `@OnEvent` listener is registered anywhere for any of these three events** — expected and correct, since Accounting doesn't exist yet; this Outbox traffic has simply been accumulating with nothing listening. **Update (Stage 3 pass):** `sales.sales_invoice.posted` and `purchases.purchase_invoice.posted` now finally have a listener each — see the roadmap item 3 below. `PaymentsReceivedService`'s events remain unlistened — no stage has needed them yet.
- **Every stock-movement confirmation event is on plain `EventEmitter2`, not Outbox**: `sales.delivery.confirmed`, `purchases.goods_receipt.confirmed`, `purchases.purchase_return.confirmed`, `sales.sales_return.confirmed` — all four currently consumed only by Inventory's own stock listeners. If Accounting is meant to auto-post Cost of Goods Sold reacting to these, CLAUDE.md §2.7's own rule ("do not rely on EventEmitter2 alone for any event... Accounting must never miss") means these need the same Outbox upgrade Purchase Invoices got in Purchases Stage 7. **Update (Stage 6/7 pass, same day):** `sales.delivery.confirmed` has since been upgraded to Outbox, and — rather than upgrading `sales.sales_return.confirmed` itself — the new `sales.sales_credit_note.issued` event was added as the Outbox-backed financial signal for sales returns (see `claude/accounting-module-status.md`'s Stage 6/7 section). `purchases.goods_receipt.confirmed` and `purchases.purchase_return.confirmed` remain plain-EventEmitter2. **Update (Stage 3 pass):** confirmed this is fine as designed — Stage 3 drives Purchases-side expense/AP recognition from `purchases.purchase_invoice.posted` (already Outbox-backed since Purchases' own Stage 7), not from the goods-receipt event, so no inventory-value-at-receipt posting exists yet and none was needed for Stage 3's scope.
- **Stage 4/5 finding — a likely pre-existing bug, not fixed as of the research/build pass, still unconfirmed as of the native-verification pass.** While building the new Bank Account create form, `journal-entry-reverse-form.tsx`'s `reversalDate` field was noticed binding directly to a Zod `.optional()` schema with an RHF default of `''` — since `.optional()` only skips validation for `undefined`, not `''`, this looks like it would fail regex validation when a user submits a reversal with the date left blank, contradicting its documented "defaults to today" behavior. Reasoned from Zod/RHF semantics only, not confirmed by running the app — **still not confirmed even after native `typecheck`/`lint`/`build`/`test` all passed, since none of those exercise real browser behavior.** Left alone (pre-existing, unrelated file, out of scope for Stage 4/5); the new Bank Account form avoids the same pattern. Worth a manual UI check on the user's machine — reverse a journal entry with the date field left blank and see what actually happens.
- **`sales_return_lines` has no monetary column at all** (checked the actual migration, not assumed) — a deliberate scope boundary from the Sales Returns stage ("physical return only, not a financial credit note"). Accounting cannot derive a revenue-reversal amount from a sales return row directly; it would need to trace back through `delivery_line → sales_order_line` to find a price, and no line currently records which invoice (if any) covered that unit. **Update (Stage 6/7 pass, same day):** resolved — see the new Sales Credit Note entity in `claude/sales-module-status.md`, which now carries exactly this traced price.
- **No `Plan`/`Feature`/`Subscription` model exists in `apps/api/prisma/schema.prisma`** (confirmed directly, its own header comment says platform/plan modeling is out of scope for this task) — `PlanFeatureGuard` cannot be built until that model exists. Not an Accounting-specific blocker; same gap as every other module.

## Terminology map — traditional Arabic accounting terms vs. what's actually being built

Asked directly during this pass ("فين دفاتر اليومية وكده") — worth spelling out explicitly so it doesn't need re-asking. In classic double-entry bookkeeping there are several named "books," but almost none of them are separate stored tables — they're different views/reports over the same two underlying tables (`chart_of_accounts`, `journal_entries` + its lines):

| Traditional term | What it actually is | Where it lives |
|---|---|---|
| دفتر اليومية (General Journal) | `journal_entries` themselves, listed in date order | The `journal_entries` table/list view (✅ Stage 2, done) — not a separate entity |
| دفتر الأستاذ (General Ledger) | Every journal line affecting one account, with a running balance | `GET /accounting-reports/general-ledger` (✅ Stage 2, done) — no stored table, matches the "never store a derivable balance" rule already applied to Sales/Purchases order totals |
| ميزان المراجعة (Trial Balance) | Every account's total debit/credit and net balance as of a date | `GET /accounting-reports/trial-balance` (✅ Stage 2, done) — no stored table |
| القوائم المالية (Financial Statements — income statement, balance sheet) | Revenue/expense accounts rolled up into net income; asset/liability/equity accounts rolled up into a balance sheet | `GET /accounting-reports/income-statement` and `GET /accounting-reports/balance-sheet` (✅ Stage 2b, done) — no stored table |

So none of these added a seventh/eighth database entity — they're reporting endpoints, all live now under `AccountingReportsController` (`/accounting-reports/*`), computed on read by `AccountingReportsService` from `journal_entry_lines` + `chart_of_accounts`.

## Competitor research (CLAUDE.md §17.2)

Focused specifically on chart-of-accounts structure and journal-entry workflow — the two pieces Stage 1 actually needed — rather than re-running the broad Egyptian/MENA ERP survey already captured in `claude/sales-module-research.md` / CLAUDE.md §17.4.

**Daftra** (the closest Egyptian-market precedent, already the reference point for prior research passes):
- Chart of accounts is a strict tree: exactly five immutable root accounts (Assets/Liabilities/Equity/Revenue/Expenses, numeric codes 1–5), branching into "main accounts" (folders, can hold sub-accounts) and finally "sub-accounts" (leaves — the only ones that can actually receive a transaction balance). Codes are unique and hierarchical (1, 11, 111). Certain account types (clients, suppliers, treasuries, warehouses) get auto-created entries when added through their own module.
- Journal entries are strictly double-entry: total debits must equal total credits to save. Automatic entries (from invoices, payroll, asset depreciation) are tagged "Auto," their account values are locked, but the description/entry number stays editable. Manual entries are fully free-form against the chart of accounts. Lines can carry a cost-center allocation and a tax association. **Applied directly to Stage 6/7's design, and now Stage 3's**: auto-posted entries use `source: 'auto'` (an already-existing enum value), mirroring Daftra's own "Auto" tagging.
- No documented formal multi-step approval workflow — only a draft/final distinction. **Applied directly to Stage 2's design**: journal entries got the same draft/posted/cancelled lifecycle as every other financial document in this codebase, and a posted entry is reversed via a brand-new offsetting entry rather than voided or deleted — preserving the audit trail, matching Daftra's own no-destructive-void precedent.

**Odoo** (general reference, not Egypt-specific): fiscal years and period locking exist as a standard concept (a "lock date" past which no new journal entry can post), consistent with building `accounting_periods` as foundational plumbing even though the master document's own entity list doesn't name it explicitly. **Applied directly to Stage 2**: `post()` is the only action gated on `AccountingPeriodsService.assertOpenForDate()` — a draft can be written for any date, matching the "closed blocks new postings, not new drafting" semantics.

**Applied to Stage 1's design:**
- The five-root / group / leaf tree shape, the `is_group`/`is_system` distinction, and "only leaves are postable" are taken directly from Daftra's model — the most relevant concrete precedent available, not invented from scratch.
- `is_system = true` is scoped to *only* the five roots, matching Daftra's "cannot be modified beyond basic properties" applying specifically to those five — everything else the template seeds is fully editable, matching the master document's own "fully editable afterward" wording literally.
- Fiscal years + accounting periods (open/closed, one per calendar month, auto-generated) are added as necessary supporting plumbing for the double-entry ledger Stage 2 built on top of — not named in the master document's entity list, called out explicitly as a schema-adjacent addition rather than folded in silently.

## Proposed full build-stage roadmap

This is the whole path to a "complete" Accounting module, laid out per the user's request. **Stages 1 through 7 are built so far, backend and frontend both.** Per CLAUDE.md §17.3, research and proposals are expected freely — actually building anything that touches a [مستقر] architectural decision (the Event Bus/Outbox split, specifically) still needs explicit approval before it's built, called out per stage below.

1. **Chart of Accounts + Fiscal Years/Accounting Periods** — ✅ done. The tree, the default Egyptian template, period open/close plumbing.
2. **Journal Entries** — ✅ done. The actual double-entry ledger: header + balanced debit/credit lines against `chart_of_accounts`, the "must balance" invariant enforced both at the service layer (across the whole line set) and by a DB CHECK constraint per line (exactly one of debit/credit), draft/posted/cancelled lifecycle, reversal-via-new-offsetting-entry for posted entries. One currency per entry — always the tenant's own `tenant_settings.currencyCode` — a deliberate deviation from the Purchases/Sales per-line-currency precedent (see `journal-entry.entity.ts`'s own comment): a general ledger only makes sense summed in one currency, and no FX-conversion layer exists yet. Manual entries only when first built — Stage 6/7 is what first adds automatic entries via `createAuto()`.
2b. **Financial Statements & reports** — ✅ done. `AccountingReportsService` + `AccountingReportsController` (`/accounting-reports/*`): General Ledger (per-account, running balance), Trial Balance, Income Statement, Balance Sheet — all computed on read, filtered to `status = 'posted'` only. Every amount is signed via a new `categoryCanonicalSide(accountType)` helper — asset/expense are debit-canonical, liability/equity/revenue are credit-canonical — used **instead of** each account's own `normalBalance`, specifically so contra accounts (e.g. code 42, Sales Returns & Allowances — `accountType = 'revenue'` but `normalBalance = 'debit'`) net correctly into their category's total rather than needing special-cased sign logic per report. The balance sheet includes a `currentYearEarnings` memo line (net income from the containing fiscal year's start date up to `asOfDate`, computed the same way the income statement computes it) so `assets = liabilities + equity` holds even though no year-end-closing process exists yet to actually post that balance into an equity account.
3. **Auto-posting from Sales/Purchases invoices** — ✅ **done**. `AccountingAutoPostingListeners` gained two more `@OnEvent` handlers consuming the Outbox-backed `sales.sales_invoice.posted` / `purchases.purchase_invoice.posted` events that had been sitting unread in the outbox table since Sales/Purchases' own earlier stages — no upstream event-publishing change needed, unlike Stage 6/7's Inventory events. Sales Invoice posting → debit Accounts Receivable / credit Revenue. Purchase Invoice posting → debit Purchase Expense / credit Accounts Payable. Reused `JournalEntriesService.createAuto()`'s idempotency machinery as-is. `accounting_settings` (migration `0054`) gained three columns: `revenueAccountId` and `accountsPayableAccountId` are auto-populated from the default template's known codes ('41', '211') the same way the Stage 6/7 fields are; `purchaseExpenseAccountId` is deliberately **not** auto-populated — the default chart-of-accounts template has no single generic "purchases expense" leaf account (only named operating-expense categories under group '52': salaries, rent, utilities, ...), so guessing one would be wrong for most tenants. It starts NULL and the purchase-invoice handler fails loudly (`BusinessRuleError`) until a tenant admin picks one via Accounting Settings. "For review" staging (§9.2) is still not built, same tracked gap as Stage 6/7 — Stage 3's two new handlers create-then-post immediately via `createAuto()`, consistent with the existing three handlers, rather than introducing an inconsistent staging behavior for only the newest two.
4. **Cost Centers** — ✅ **done.** A flat (non-hierarchical) tagging dimension: a new `cost_centers` table, plus a nullable `cost_center_id` FK (`ON DELETE SET NULL`) on `journal_entry_lines`, matching Daftra's own precedent that lines "can carry a cost-center allocation." No delete-guard needed — deleting a cost center just un-tags any lines that used it. Full CRUD screen plus a per-line `<Select>` in the journal-entry line editor and a read-only column on the entry details view.
5. **Bank Accounts** — ✅ **done.** A `bank_accounts` entity (one per linked `chart_of_accounts` leaf, enforced `UNIQUE`), plus `is_reconciled`/`reconciled_at` columns added directly to `journal_entry_lines` rather than a separate reconciliation table (a line only ever belongs to one bank account's register). Built exactly to the scope this roadmap entry called out: a register view (reusing `JournalEntryLineRepository.listPostedByAccount()` against the bank's linked GL account, signed via the same `categoryCanonicalSide` helper the reports use) with a manual per-line reconcile/unreconcile toggle — **not** full statement-import reconciliation, which remains a possible future competitive enhancement, not built. Full detail in `claude/accounting-module-status.md`'s Stage 4/5 section.
6. **COGS auto-posting from stock movements** — ✅ **done** (same-day follow-up pass, approved by the user). Built exactly as flagged: `sales.delivery.confirmed` upgraded from plain EventEmitter2 to Outbox. Went one step further than originally scoped, discovered necessary during design: rather than Accounting listening to `sales.delivery.confirmed` directly (a race condition — `OutboxDispatcherService.emitAsync()` gives no ordering guarantee between Inventory's and Accounting's sibling listeners for the same event), Inventory's own stock listener now publishes a derived, Outbox-backed `inventory.stock_consumption.recorded` event carrying the resolved unit cost, and Accounting reacts to that instead. Full detail in `claude/accounting-module-status.md`'s Stage 6/7 section.
7. **Sales Returns financial handling** — ✅ **done** (same pass). The user chose the real-financial-credit-note design over deriving a reversal amount by tracing back to the original invoice line. Built as a new Sales Credit Note entity (Sales module, migration `0053`), auto-created by `SalesReturnsService.confirm()`, priced from the original `sales_order_line.unitPrice`. Its `sales.sales_credit_note.issued` outbox event drives Accounting's revenue-reversal auto-posting (Dr Sales Returns & Allowances / Cr Accounts Receivable). Full detail in `claude/accounting-module-status.md`'s Stage 6/7 section and `claude/sales-module-status.md`.
8. **Tax Returns (`tax_returns`)** — the master document names this entity but gives no detail; genuinely Egypt-tax-specific and adjacent to the still-deferred ETA e-invoice work. Proposed as its own dedicated research pass when picked up, not bundled into this stage's work. **Still not built — this is the one remaining item in the Accounting module's roadmap, and the only remaining item across the whole platform's fixed build order** (Inventory/Purchases/Sales/Accounting Stages 1–7 are all complete, backend and frontend, with native verification also confirmed passing — see `claude/accounting-module-status.md`).

Stages 1 through 7 are all done now, backend and frontend, with native `pnpm typecheck`/`lint`/`build`/`test` all confirmed passing as of 2026-08-30 (see `claude/accounting-module-status.md`'s "Verification status" section). Stage 8 (Tax Returns) is the only remaining item and needs its own dedicated research pass first — it's genuinely Egypt-tax-specific and adjacent to the still-deferred ETA e-invoice work, not a simple extension of anything already built.
